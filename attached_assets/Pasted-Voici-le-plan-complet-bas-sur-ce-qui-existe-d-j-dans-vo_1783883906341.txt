Voici le plan complet, basé sur ce qui existe déjà dans votre codebase (pas de réinvention — on branche sur l'infra déjà là : SyncLogRepository/SyncService pour la réconciliation, MessagingServer/MessagingService pour le temps réel, TransferService pour le transfert de fichiers en chunks, Users.role et AuthorizedMachineRepository pour les droits).
Constat d'architecture important
Votre appli n'est pas un mesh P2P pur : c'est un modèle SERVER / CLIENT avec failover (--role SERVER/CLIENT, ElectionService, priority_weight, doc HYBRID_SERVER_FAILOVER.md). Un seul poste fait autorité à la fois. Le pattern déjà utilisé pour Messages/Groups/Users est :

Chaque écriture → une entrée dans SyncLog (table_name, operation, payload_json, lamport_clock, origin_machine_id)
Diffusion temps réel via le canal WebSocket existant (MessagingServer/MessagingService)
Rattrapage après coupure via SyncService (sync_request → sync_batch → sync_ack)

Le plan ci-dessous fait pareil pour SharedFolders/SharedFiles, plutôt que d'inventer un SyncProtocol isolé comme le suggérait le doc de conception d'origine.

A. Partage réseau
A1 — Métadonnées : brancher SharedFolders/SharedFiles sur le SyncLog existant

À chaque createFolder, removeFolder, et à chaque changement détecté par SyncEngine (Create/Update/Delete/Rename déjà journalisés dans SyncOperations), écrire aussi une entrée SyncLog (table_name = "SharedFolders" ou "SharedFiles"), exactement comme le font déjà MessageRepository/GroupRepository.
Ça donne gratuitement : rattrapage automatique via SyncService existant quand un poste se reconnecte, sans nouveau protocole.

A2 — Diffusion temps réel

Nouveau type de message WebSocket (à côté de "message", "sync_request", etc.) : "shared_folder_event", broadcasté via MessagingServer::broadcastMessage() dès qu'un SharedFolder/SharedFile change localement (branché dans SharedFolderContext/SyncEngine).
Les autres postes reçoivent l'event, mettent à jour leur vue SharedFolders (liste de dossiers, compteur fichiers) — sans télécharger le contenu tout de suite, juste les métadonnées (nom, hash, version, taille).

A3 — Transfert du contenu réel des fichiers

Réutiliser TransferService/FileTransferService existants (déjà chunkés, avec reprise — vous avez déjà test_transferresumeintegration). Ajouter un mode "récupérer ce SharedFile" qui télécharge le fichier manquant/modifié depuis le poste qui l'a, et l'écrit dans le local_path du dossier partagé local.
Un poste qui rejoint un dossier partagé déjà existant ailleurs télécharge tous ses fichiers via ce mécanisme (Phase 6 du doc d'origine), poste par poste, un fichier à la fois.

A4 — Conflits (à traiter après A1-A3)

Détection simple par version/hash divergent → renommage fichier (conflit-MachineX).ext, comme suggéré dans le doc d'origine. Pas besoin de résolution intelligente dans un premier temps.


B. Permissions
B1 — Modèle de données
Nouvelle table SharedFolderAccess :
sqlCREATE TABLE SharedFolderAccess (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    folder_id   INTEGER NOT NULL REFERENCES SharedFolders(id) ON DELETE CASCADE,
    user_id     INTEGER REFERENCES Users(id),   -- NULL = "tout le monde"
    role        TEXT NOT NULL DEFAULT 'read_write',  -- 'read_only' | 'read_write' | 'admin'
    UNIQUE(folder_id, user_id)
);

Par défaut à la création d'un dossier : une ligne (folder_id, user_id=NULL, role='read_write') → équivalent au comportement actuel ("tout le monde", cf. Phase 12 du doc). Pas de régression.
Les admins (Users.role = 'admin', déjà existant) ont toujours accès total, sans ligne dédiée.

B2 — Vérification côté métier

SharedFolderManager prend en compte l'appelant (ownerId/userId déjà passé partout) pour filtrer getFolders() selon l'accès, et refuser shareFolder()/écriture de fichiers si read_only.
SharedFolderContext (déjà wired à UserManager::currentUserId()) refuse côté UI avant même d'appeler le manager.

B3 — UI de gestion des droits

Dans SharedFolderView.qml, ajouter un petit panneau "Partagé avec" sur chaque dossier (liste des utilisateurs + leur rôle), réutilisable avec le style déjà présent dans AdminView.qml/UsersView.qml.

B4 — Propagation réseau des droits

SharedFolderAccess suit le même mécanisme que A1 (entrée SyncLog + diffusion shared_folder_event), donc les changements de droits se propagent comme le reste.


Ordre d'implémentation suggéré

B1 + B2 (permissions de base, tout en local, pas de réseau) — rapide, débloque déjà "tout le monde a accès" → "accès contrôlé", même en solo.
A1 (SyncLog pour SharedFolders/SharedFiles) — réutilise l'existant, risque faible.
A2 (broadcast temps réel des métadonnées) — rend le dossier visible chez les autres.
A3 (transfert réel des fichiers via TransferService) — le dossier devient vraiment utilisable à distance.
B3 + B4 (UI + propagation réseau des droits) — finalisation.
A4 (conflits) en dernier, une fois le reste stable.
